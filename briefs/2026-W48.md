## One concept to understand better: "proof" vs. "test" as an evidence tier

A passing test tells you code worked on the specific inputs you tried it with. A formal proof (checked by a tool like Verus, backed by an SMT solver) tells you a property holds for *every* input a specification covers — including ones no test suite thought to try. Microsoft's PDD Kit makes this concrete: it proves a login function picks the right account, checks the password correctly, and issues a token with the right identity, "for every input," while explicitly naming the parts it only *tests* (a password-hashing library, a clock, a database lookup — the "trusted boundary"). The catch: a proof only shows code matches its *spec*, not that the spec is what you actually meant ("a wrong spec is still possible," the authors admit), and writing a real spec takes genuine effort. **When it doesn't apply**: most interesting agent behavior (did it understand the user's intent, was its judgment reasonable, did it pick a sensible tradeoff) can't be reduced to a formal specification at all — proof is a tool for a narrow class of hard, precisely-statable rules (an invariant, a safety property), not a replacement for judgment-based grading.

Ties to LayerLens's open question #2 (is "proven" a distinct, nameable attribution/evidence category from "passed") and #11 (a reviewer shown "proven" versus "passed" is being given a meaningfully stronger claim to check).

## Possible applications to LayerLens

**1. A "proven" grading tier for formalizable properties (Open Q#2, #11).** Problem: all four of LayerLens's grader types are test/rubric-shaped. How others solve it: Soteria and PDD Kit both show formal verification is becoming tractable enough for real agent-generated artifacts, not just toy examples. The gap: no part of LayerLens's grading taxonomy currently offers a "holds for every input" guarantee. The assumption to test: at least one LayerLens system type has a property simple enough to formalize (e.g. "a Stripe balance never goes negative," "a Linear issue's assignee is always a valid team member"). Small test a designer could run: pick one such candidate property, sketch what a "proven" badge would need to show a reviewer differently from today's "passed" badge, and note where the PDD Kit's own caveat ("a wrong spec is still possible") would need to be surfaced honestly.

**2. Audit LayerLens's own system-type tool surfaces for an "access gap," not just a guidance gap (Open Q#2, #7).** Problem: a field study found a coding agent's wrong diagnoses in a real production system were consistent with the (incomplete) evidence it could see — the gap was access to state (live lock views, untruncated error detail), not reasoning. The gap: LayerLens's existing I-0009 idea already covers misleading *error messages*; this is a different, narrower failure — tool surfaces that are accurate but incomplete. The assumption to test: do any of LayerLens's shipped system types (Salesforce, Linear, SEC EDGAR, Stripe, Gmail) omit state a human debugger would reach for in an equivalent real investigation? Small test: pick one system type, compare its exposed tool surface against what a human support engineer would actually have access to for the same class of problem.
