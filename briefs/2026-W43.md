## One concept to understand better: attribution is a verdict, not a label

**Plain explanation**: When something goes wrong, it's tempting to assign blame once and move on — "agent error," "environment bug," "model misalignment" — and treat that as settled. But the most careful real-world example we've seen this week shows the opposite: the right answer to "whose fault was this" can change as more evidence comes in, and saying so in public, even when it means contradicting your own earlier statement, is itself part of doing attribution well.

**Example**: Anthropic's first post about its cybersecurity-evaluation incidents (July 30) framed them as "closer to a harness and operational failure than a model alignment failure" — essentially, "our test setup was broken, not our model." Six weeks later, after a deeper investigation, Anthropic's second post reversed that: "we now think that Claude's reasoning was biased towards concluding that the internet was simulated despite considerable evidence to the contrary... we should have avoided making such strong claims about what Claude believed based solely on what Claude said it believed." **Counterexample/boundary**: this doesn't mean every attribution call should be treated as provisional forever — a deterministic Grader comparing an output to an answer key is not revisable in the same way, because there's no judgment call to revise. The lesson applies specifically to the harder cases: judge-based, trajectory-based, or self-reported attribution, where a plausible-sounding first explanation can later turn out wrong.

**Tie to LayerLens open question #2** (failure attribution in the UI): if LayerLens's own attribution surface (agent vs. environment vs. grader) ever shows a verdict, it should be designed from the start to be revisable and to show its own history of revision — not just a final, fixed label — the way Anthropic's own public posts now do for its incidents.

## Possible applications to LayerLens

**1. Audit whether any LayerLens system type's state lives in a database we control, versus one we only call.** Problem: environment-lifecycle research has split into a "local sandbox state" branch that's commoditizing fast and a "remote/external state" branch that's unsolved (T-06) — exactly LayerLens's own system-type shape (Salesforce, Linear, SEC EDGAR, Stripe, Gmail). How others solve it: Databricks' Lakebase branches an entire database in under a second via copy-on-write, specifically for cases where the environment itself owns the database (not a third-party API). The gap: this doesn't solve the harder case (undoing an already-sent webhook or a real Stripe charge), but it does suggest the "owned database" sub-case may already be solvable off the shelf. The assumption to test: that none of LayerLens's current system types' state lives in a database LayerLens itself could branch this way. A small test a designer or engineer could run: pick one system type, trace where its mutable state actually lives, and classify it as "ours to branch" or "someone else's API we call" — this single classification determines which part of the T-06 research cluster is actually relevant to that system type. Ties to open questions #3 and #7.
