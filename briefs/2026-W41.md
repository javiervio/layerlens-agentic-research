## One concept to understand better: the agent-OS semantic gap (and its cousin, the agent-world semantic gap)

**Plain explanation**: Crab's paper names a specific problem: an agent framework sees model turns and tool calls, but not their complete operating-system effects (which files changed, which processes started); the operating system sees file and process activity, but has no idea which agent "turn" caused it or whether it matters for recovery. Neither side alone has enough information to checkpoint intelligently — you need something that watches both and correlates them.

**Example**: if an agent's turn only reads a file and reasons about it, there is nothing to checkpoint — rolling back to before that turn and after it would restore identical state. If a turn edits three files and starts a background process, that is exactly the moment a checkpoint earns its cost. Crab's "Inspector" component exists specifically to tell these two cases apart automatically, at the OS level, rather than trusting the agent's own account of what it changed.

**The cousin problem, which is *not* solved by the same mechanism**: ACRFence names what you could call an agent-world semantic gap — the agent framework sees "I rolled back to before I sent that approval request," but the external service that received the original request has no idea a rollback happened; from its point of view, a second, slightly-different-looking request just arrived, and it has no way to know the first one should be considered undone. This is a fundamentally different kind of gap (not OS-visible state, but another organization's server state) and nothing in Crab's mechanism addresses it — which is exactly why Crab states its own limit so plainly.

**When it does not apply**: read-only tool calls (nothing to roll back) or systems entirely inside LayerLens's own minted environment (where the "world" the agent-OS gap needs to track is the whole environment, not someone else's server). It applies most sharply wherever an agent's action has a real, observable effect outside the sandbox LayerLens controls — exactly LayerLens's system types.

**Tied to LayerLens open question #7** (human control and recovery): if LayerLens ever lets a user checkpoint/branch a run that wrote to Salesforce or Stripe, "did the local restore work" (an agent-OS-gap question, increasingly solved elsewhere) is a completely different question from "is it safe to resume from here" (an agent-world-gap question, which nobody in this corpus has solved generally).

## Possible applications to LayerLens

**Problem**: if LayerLens ever ships a checkpoint/branch or "undo" affordance over an environment that writes to a real connected system type (Salesforce, Stripe, Linear, Gmail, SEC EDGAR), a naive implementation risks exactly ACRFence's two attack shapes: replaying an already-executed write, or resurrecting an already-consumed credential/approval.

**How others solve it**: Crab solves the local half (what changed in the sandbox) well, but explicitly refuses to touch the remote half. ACRFence's proposed mitigation is "replay-or-fork" semantics at the tool boundary: either genuinely replay the exact prior effect (recognizing it as a repeat, not a new action) or fork into a clearly distinct new branch, but never silently re-execute as if nothing happened. Recoverability-as-a-System-Primitive (C-0034, still unvalidated) proposes a separate governance layer that records *which rule* permitted a resumption, independent of whether the restore was technically correct.

**The gap**: nobody in this corpus has shown a working, demonstrably-safe version of this for a product surface a real (non-expert) user interacts with — every source here is infrastructure-level or security-research-level, not a UX pattern.

**The assumption about our product**: LayerLens's "trust wall" pattern (never serving the seed/knobs to an agent-facing key) is a close conceptual cousin of what's needed here — a boundary the agent cannot see past. The open design question is whether that same instinct (a boundary the agent-facing surface cannot bypass) can be extended to writes against connected systems: record every write with enough information (an idempotency key, a "has this already been sent" marker) that a rollback can tell a genuine replay from an accidental duplicate.

**A small test a designer could run**: pick one of LayerLens's shipped system types that supports a write action (e.g., Stripe or Salesforce). Sketch, on paper, what information a rollback-to-before-this-write would need to record at write time (not after) to let a later "undo" distinguish "this write never actually reached Stripe" from "this write reached Stripe and must not be sent again." If the honest answer is "we don't currently record that," that is itself the finding — a cheap, concrete gap-check tied directly to open question #7.
