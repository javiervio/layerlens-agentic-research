## One concept to understand better: pass@k versus pass^k

**Plain-language explanation**: pass@k asks "if I let the agent try k times, does at least one attempt succeed?" — a capability question, useful when any single success counts (like sampling several code completions and keeping the best one). pass^k asks "if I run the agent k times, do *all* k attempts succeed?" — a reliability question. An agent can have high pass@k and low pass^k at the same time: it can usually find a way to succeed eventually, while still failing unpredictably on any given attempt.

**Example**: a hypothetical agent that succeeds 80% of the time, independently, on each attempt has pass@5 near 100% (it's very likely at least one of five tries works) but pass^5 of only about 33% (0.8^5) — all five tries succeeding is a much higher bar. The gap between those two numbers *is* the reliability problem, in one arithmetic step.

**When it does not apply**: pass@k is the right lens when your product only needs one good outcome and can discard the rest (e.g., generate five draft summaries, a human picks the best). It's the wrong lens whenever the agent runs unsupervised and every single run needs to be trustworthy — which is closer to how a production agent, or a LayerLens environment run, actually gets used.

**Tie to LayerLens open question #5**: "A new model call does not guarantee the same trajectory; how do we express variation across attempts (reliability versus one lucky pass)?" — pass@k vs pass^k is a ready-made vocabulary for that exact question, pending a direct read of the paper that proposed it (see signal #2).

## Possible applications to LayerLens

**1. Problem**: A single accuracy/pass number can hide a real tradeoff (cost, reliability) that determines whether an agent is actually usable. **How others solve it**: HAL's Pareto-frontier framing (signal #3) — never rank on accuracy alone; always show it against at least one other axis. **The gap**: We don't know whether LayerLens's own comparison surfaces (model head-to-head, Optimize) currently default to showing a single "winner" without a cost or reliability axis alongside it. **The assumption about our product**: The "grid refuses to average across mismatched versions" differentiator (from last week's tau2-bench finding) handles version-mismatch, but that's a different problem from tradeoff-blindness — a comparison can be perfectly version-matched and still hide a 10x cost difference behind a 1-point accuracy edge. **A small test a designer could run**: Pull up three existing LayerLens comparison views and check, for each, whether cost or reliability is visible by default next to the primary score, or requires a click to surface. Ties to open question #1.

**2. Problem**: Before an agent takes a risky action, a confirmation needs to actually inform the decision, not just gate it. **How others solve it**: Nobody found this week has a published answer either — Magentic-UI (signal #4) has the gating mechanism (three approval tiers) but the consequence-preview question is unresolved in what we could read. **The gap**: the field currently seems to treat "should I ask permission" and "what do I show when I ask" as separate, and mostly only answers the first. **The assumption about our product**: LayerLens's confirmations may currently be generic approve/deny, same as what we found (or didn't find) for Magentic-UI — untested. **A small test a designer could run**: Pick one LayerLens action that writes to an environment (e.g., running a task against a real system) and check whether its confirmation, if one exists, names the specific record or field that will change, versus a generic "are you sure?" Ties to open question #7.
