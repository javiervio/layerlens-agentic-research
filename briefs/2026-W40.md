## What deserves your attention

**1. The reliability thesis picked up a third independent family this week — and the exact vocabulary we used two weeks ago turns out to have a real implementation trap.** [research] "Identical Runs, Different Results" ran 584 real benchmarking runs of coding agents on open-weight models and found that running the *same* agent-model pairing repeatedly varied MORE than different pairings varied from each other (median 0.0107 AUC run-to-run vs. mean 0.0095 AUC agent-to-agent). Three-run comparisons — a realistic sample size — ranked agents unreliably; the authors estimate it would take tens to 100+ runs to resolve real differences. [Source](https://arxiv.org/abs/2609.33812) — read directly via the companion GitHub repo. Separately, a deliberate search for critiques of the pass@k/pass^k vocabulary from two weeks ago turned up a genuine catch: some benchmarks compute "pass@k" by substituting unit-test counts for independent rollout attempts, which the authors show can inflate scores from ~0.96-0.97 down to a true ~0.00-0.12 once corrected — a 4x inflation on real SWE-bench tasks (0.80 hidden-test pass rate vs. 0.20 strict resolve rate). [Source](https://arxiv.org/abs/2608.14711) (via [companion repo](https://github.com/nv78/Research-CodeBench), read directly). Why it matters: this doesn't undercut the reliability story — it strengthens it (the true gap may be worse than reported) — but it's a concrete build caution for anything LayerLens ships under a "pass^k" name (F-0001): the k attempts must be genuinely independent full-task rollouts.

**2. Three unrelated teams converged on the same "snapshot, rollback, fork" environment-state mechanism this week — none of them made it legible to a human.** [research + competitive] DeepSeek's DSec (industrial infra scale), Planarian (Imperial/Microsoft-affiliated, agent-runtime recovery — generalizes the pattern to *remote* service state via "compensating actions," not just local sandbox state), and Counterfactual Rollout Replay (RL training reward-shaping) all independently built checkpoint/rollback/fork as their core mechanism, for three different reasons. [Planarian](https://arxiv.org/abs/2609.35366) reports up to 15x task-quality improvement from undo/parallel exploration at only 3% overhead. Why it matters: this promotes a new thesis, T-06 — the mechanism is commoditizing fast across independent teams; legibility to an actual user (what state persists, when it ends, a visible checkpoint/branch affordance) is the gap none of them address, and it's the closest external match yet to LayerLens's own deterministic-replay story, especially Planarian's remote-state generalization (our Salesforce/Linear/Stripe system types ARE "remote state").

**3. Tool error messages written for humans actively mislead agents — and more capable agents follow the bad advice more, not less.** [research] In 150 widely-used MCP servers, 949 of 3,001 error messages tell the calling agent to do something it can't (run a terminal command, edit a config) — and on expired credentials, the cost of following that bad advice grew from 18 points lost (GPT-5.5) to 69 points lost (GPT-6 Astra) as models got more capable. [Source](https://arxiv.org/abs/2609.35381). Naming an actual tool call in the error message instead raised recovery from 45% to 84%. Why it matters: this is a concrete, testable property of exactly the real-API system types LayerLens ships (Salesforce, Linear, SEC EDGAR, Stripe, Gmail) — not a hypothetical.

**4. Connection: two independent findings this week both show capability does NOT self-correct for bad environment/interface design — it can make the damage worse.** [connection] Signal #3 above (MCP errors: more capable = more harmed) and a second, separate finding this week — a benchmark-maintenance paper found confirmed violation rates on SWEBench Pro rose from 24% to 73% between two successive model generations before later models improved — [Source](https://arxiv.org/abs/2609.34262) — both show the same shape: a flawed surface gets exploited *more* as models get smarter, not less. Why it matters: this is a direct, evidence-backed counter to "the models will just get better and evals/environments won't matter as much" — it argues the opposite. New thesis T-07, still early (two families).

## One concept to understand better: reliability@k versus (broken) pass@k

**Plain-language explanation**: Two weeks ago we covered pass@k ("did at least one of k tries succeed?") vs. pass^k ("did all k tries succeed?"). This week surfaced a sharper problem underneath both: what counts as "one try" in the first place. Some benchmarks compute k by counting *unit tests inside a single submission* rather than *independent full-task attempts* — treating five correlated sub-checks of one run as if they were five separate rolls of the dice. That's not a small rounding error; it can make a near-zero reliability number look like it's in the 0.95+ range.

**Example**: on real SWE-bench tasks, the mean *hidden-test pass rate* (how many individual tests pass, averaged) was 0.80 — looks great. The *strict resolve rate* (did the whole task actually get solved, correctly, as one attempt) was 0.20. Same underlying runs, 4x different number, depending on which one you report as "reliability."

**When it does not apply**: if you're only ever reporting single-task, single-attempt pass/fail (no k involved at all), this specific trap doesn't apply — it's specifically a hazard for anything that reports a "k attempts" or "reliability score" style number.

**Tie to LayerLens open question #5**: if F-0001 (a pass^k-style readout) gets built, this is the one thing to get right on day one: count genuinely independent, full-task rollouts as the "k," never sub-checks within one run. Getting this wrong would mean shipping exactly the kind of quietly-inflated reliability number the rest of the field is currently learning to distrust.

## Possible applications to LayerLens

**1. Problem**: Our own shipped system types (Salesforce, Linear, SEC EDGAR, Stripe, Gmail) wrap real, human-authored APIs — which means they very likely carry the same human-oriented error-message pattern the MCP paper documents (signal #3). **How others solve it**: nobody yet — the paper's own fix (name the actual tool call in the error step) is a research recommendation, not a shipped pattern we found anywhere. **The gap**: we don't know whether our own tool error surfaces already do this or not. **The assumption about our product**: untested — this could be a quick, cheap win or a non-issue. **A small test a designer could run**: pull the actual error responses our environments return for 3-5 common failure cases (expired auth, rate limit, missing record) across two system types, and check whether each one names something the agent can actually call, versus a human-oriented instruction. Ties to open question #2, feeds I-0009.

**2. Problem**: users cannot see what state a LayerLens environment keeps across a run, when it ends, or cheaply branch a run to try a variant (open question #7). **How others solve it**: Planarian's snapshot/rollback/fork on both local AND remote state (signal #2) is the closest match found yet. **The gap**: three independent teams built the mechanism; none made it visible to an end user — that's the opening. **The assumption about our product**: LayerLens's deterministic minting already gives a natural "replay" story; whether that's currently surfaced as anything like checkpoint/branch is unconfirmed. **A small test a designer could run**: sketch what a checkpoint/branch affordance on an environment run would look like, specifically for a remote system type (e.g. "branch this Salesforce environment, try a different starting state, compare"). Ties to open question #7, feeds I-0007 (now L1).
