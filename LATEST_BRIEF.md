## One concept to understand better: declared isolation versus verified isolation

**Plain explanation**: Saying an environment is "sandboxed" or "offline" is a design intent, not a proof. Isolation has to be checked at every boundary a request could cross — the sandbox's own network rules are one boundary, but the model's own inference-serving layer is a separate one, with its own capabilities (like fetching a URL server-side) that the sandbox's network policy was never built to see, because that fetch never happens inside the sandbox at all.

**Example**: Prime Intellect's "offline" evaluation sandbox genuinely had no network access of its own — but the inference API serving the model inside it did, and a provider feature that tells the *server* to fetch a file was a path the sandbox's isolation never covered. **Counterexample/boundary**: this doesn't apply to an environment with no model-serving dependency at all (a fully local, self-contained simulation) — the gap specifically appears wherever a hosted inference provider sits between "the agent" and "the sandbox."

**Tie to LayerLens open question #3** (deterministic replayability as a surface): if LayerLens's trust wall is to be shown and trusted, not just asserted, it needs an answer to "which boundary does this guarantee cover, and which doesn't it" — the same discipline this week's incidents show two sophisticated infrastructure teams got wrong.

## Possible applications to LayerLens

**1. Audit LayerLens's own system types for the inference-layer side-channel class.** Problem: an environment's declared isolation can be silently bypassed through the model-serving layer rather than the sandbox itself (Prime Intellect, this week). How others solve it: patch the inference engine and extend egress controls to cover it explicitly (vLLM/SGLang/TensorRT-LLM, per Prime Intellect's own remediation). The gap: LayerLens's system types (Salesforce, Linear, SEC EDGAR, Stripe, Gmail) are API/record-based rather than sandboxed-execution-based, so the exact mechanism may not transfer directly — but the *principle* (verify every boundary a request can cross, not just the one you built on purpose) does. The assumption to test: that LayerLens's agent-facing key boundary (the trust wall) has no equivalent side channel through a model provider's own built-in tool-use or fetch capabilities. A small test a designer or engineer could run: for one system type, trace exactly which network/API calls an agent's tool use can trigger, and confirm none of them resolve through a path that bypasses the environment's own grading/answer-key boundary. Ties to open question #3.

**2. Pin harness/scaffold as a first-class dimension in comparison views.** Problem: a 1-point accuracy edge, or even a clear winner, can flip entirely depending on which harness ran the agent (this week's "Finding the Right Fit," up to 30 points). How others solve it: nobody yet — this is a documented gap, not a shipped answer. The gap: LayerLens's own model-comparison and Optimize views would need to confirm they surface (not just internally track) which harness/scaffold produced a given score. The assumption to test: that two runs being compared in LayerLens today are using the same harness/scaffold, and that this is visible to the person comparing them, not assumed. A small test: pull up an existing model-comparison view and check whether harness identity is shown anywhere, or only model identity. Ties to open question #1.
